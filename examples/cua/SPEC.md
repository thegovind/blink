# blink CUA scenarios: shared contract

This contract describes the offline apps and their local agent harness. The oracle is for
scoring and the CPU mock; it is never shown to the model.

## Why this exists

blink answers typed questions (choice / yes-no / score) about a state in one forward pass per
question and returns a probability for every offered option. No text is generated.
`blink-mimo-9b` reads screenshots with its own vision encoder (XiaomiMiMo/MiMo-V2.6-Distill-Qwen-9B,
27 blocks, hidden 1152, unchanged by blink training). The goal here is a set of realistic
computer-use (CUA) scenarios that blink drives **from pixels**, recorded as real-speed videos
and measured over many seeded runs, for the Space, docs and model cards.

## Layout

```
examples/cua/
  SPEC.md                 this contract
  apps/
    registry.json         generated by build_registry.py from every <app>/scenario.json; never hand-edit
    build_registry.py     merges the per-app scenario.json files (each builder owns its own apps)
    common/blink-scenario.js  shared helper: URL params, seeded RNG streams, register() for the contract
    <app>/index.html      one folder per app; all assets inline or relative
    <app>/scenario.json   that app's registry entry (schema below)
  harness/                Python agent loop, marking, recorder, sweep runner, metrics
  tests/                  unittest/pytest for both halves (CPU only, no model)
  runs/                   outputs; gitignored except files a later step promotes
```

## Apps (built by the apps builder)

- Self-contained static pages served from `examples/cua/apps/` by a plain static HTTP server.
  No network access, CDNs, remote fonts or images; draw icons with inline SVG/CSS; use system
  font stacks. Original designs only: no real brand names, logos or copied layouts.
- Deterministic given URL params:
  - `seed=N` (default 1) varies content, names, prices, order of lists and small layout details;
  - `task=K` (default 0) picks the task;
  - `interrupts=0|1` (default 0) lets a seeded cookie banner or modal appear once mid-task;
  - `theme=light|dark` (default light);
  - `state=<name>` opens directly in a named state (for classification sets, see below).
- Designed for screenshots at viewport 960x576 CSS px with deviceScaleFactor 1.5
  (the model reads 1440x864 pixels). The phone app uses 390x844 at scale 1.5.
- Every actionable element is one of: `a[href]`, `button`, `input` (not hidden), `select`,
  `textarea`, or an element with role `button|link|tab|checkbox|radio|switch|menuitem|option`.
  Give each a short, unique, visible label (text or aria-label). Keep **at most 16 candidate
  elements visible per screen** by design (tabs, pagination, progressive screens).
- Tasks need 3 to 10 actions. Some tasks include a **risky** final step (pay, send, delete,
  share, publish) that goes through a confirmation dialog. Any text the agent must type
  appears in the task in double quotes and is listed in `values`.
- Native `<select>` is allowed; the harness picks an option by a follow-up question.
- Contract object on `window` (a shared helper in `common/` is fine):

```js
window.blinkScenario = {
  id: "shop", seed: 3, taskIndex: 0,
  task: "Buy the \"Trail Runner 2\" shoes in size 42 and pay with the saved card.",
  values: ["Trail Runner 2", "42"],        // strings the agent may type; [] if none
  check() {                                 // ground truth, recomputed on every call
    return {done: false, success: false, detail: "cart empty"};
  },
  expected() {                              // oracle for scoring and teacher data; never shown to the model
    return {selector: "#add-to-cart", action: "click", value: null, done: false, risky: false};
    // action: "click" | "type" | "select" | "none" (when done). For "type"/"select", value is the
    // exact string. risky: true when the next correct action pays/sends/deletes/shares.
    // Canvas apps return {target: "<targets() id>", ...} instead of selector.
  },
  state() { return "product"; },           // current named state (see registry states)
  targets: null,                            // canvas apps only: () => [{id, name, role, rect:{x,y,w,h}}] in CSS px
};
```

- `success` must also be false if the agent caused a forbidden side effect (wrong item bought,
  wrong file deleted, message sent to the wrong person). `check()` never throws.
- Canvas apps (`desktop`, `game`) draw everything on `<canvas>` and expose `targets()` with hit
  regions (what a UI detector would return). The harness clicks real mouse coordinates at a
  target's centre; the app hit-tests. The model never gets names for canvas targets.

### registry.json (built from each `<app>/scenario.json`, one scenario object per file)

```json
{
  "version": 1,
  "scenarios": [
    {
      "id": "shop", "title": "Buy the right thing", "path": "shop/index.html",
      "viewport": {"width": 960, "height": 576}, "scale": 1.5, "kind": "dom",
      "tasks": [{"index": 0, "summary": "buy shoes, pay (risky)", "optimal_steps": 7, "risky_steps": 1}],
      "states": [{"name": "cart", "labels": {"page_kind": "cart", "modal": false, "error": false, "signed_in": true}}]
    }
  ]
}
```

`states[].labels` feed a screen-state classification set: use the same label keys across apps:
`page_kind` (one of `home, list, detail, form, cart, checkout, confirm, inbox, message, settings,
calendar, files, search_results, error, login, dialog, game`), `modal` (bool), `error` (bool),
`signed_in` (bool), `loading` (bool).

## Harness (built by the harness builder)

- Python 3.12, `playwright` (async), `pillow`, `httpx`. Mark screenshots with the Space's own
  `space/screens.py` `mark()` / `layout()` so the pixels match what blink was probed on.
- Candidate elements for DOM apps: visible, enabled elements from the selector list above, inside
  the viewport, de-duplicated (outermost actionable wins), in reading order, capped at 16. Canvas
  apps: `blinkScenario.targets()`.
- One step = clean screenshot -> numbered boxes burnt in -> one POST to blink `/v1/systemone`:

```json
{"model": "blink",
 "state": {"task": "...", "previous_actions": ["clicked box 3 (Search)"],
           "screenshot_note": "Use the attached screenshot with boxes 1-7.",
           "screenshot": "data:image/png;base64,..."},
 "questions": {
   "element": {"type": "choice", "instructions": "Which marked element should the agent act on next to make progress on the task?",
               "criteria": {"1": "box 1", "2": "box 2"}},
   "done":  {"type": "noul", "instructions": "Is the task already complete, without another element action?",
             "criteria": {"true": "No more element action is needed", "false": "Another element action is needed"}},
   "risky": {"type": "noul", "instructions": "Would the next click for this task be risky or hard to undo?",
             "criteria": {"true": "It pays, sends, deletes or shares something that cannot be taken back",
                          "false": "It only opens, selects, searches or filters"}}}}
```

  These strings are the Space's (`space/screens.py`); import them rather than copying.
  Response: `answers.<q>.choice`, `answers.<q>.probabilities` (option -> p), `usage.visual_tokens`.
- Decision rule (the Space's): stop when p(done) >= 0.60; gate when p(risky) >= 0.50 (in the demo the
  gate shows "Ask before clicking N" and is auto-approved after a visible beat; the eval records it).
  Otherwise act on the top element. Text inputs: a follow-up `value` choice over `values`
  ("Which value from the task belongs in the selected field?"). `<select>`: a follow-up choice over
  its option labels. Previous actions are the agent's own memory (e.g. `typed "42" into box 5 (Size)`).
- Step limit: `optimal_steps * 2 + 4`. Also stop after 3 identical consecutive actions.
- Game-mode exception: at the scenario's cadence, several lane decisions are required per
  wave; use `optimal_steps * 4 + 8` ticks for a game with a declared cadence, and do not
  treat a repeated safe lane as a stuck UI action. If the game offers `pause(true)` and
  `advance(ms)`, hold simulation during inference and advance one cadence per decision;
  record simulation time separately from request latency and video display time.
- Outputs per episode, in `runs/<run_id>/<scenario>/<task>-<seed>-<model>/`:
  `trace.jsonl` (one line per step: step, t_start/t_end, url, state(), candidates [{n, box, role, name}],
  marked screenshot file, request questions, answers with probabilities, chosen action, wall_ms,
  expected() at that step, gate fired, check() after the action), `steps/NNN.png` (marked screenshots),
  `video.webm` (real speed), `summary.json` (success, steps, optimal_steps, gates, per-step
  element accuracy vs expected, p50/p95 wall_ms, model, server, seed, harness git sha).
- Video: Playwright `record_video` at the viewport size times the scale. After the clean
  screenshot is taken, draw an in-page overlay (pointer-events: none) with the same numbered boxes, then
  on the answer highlight the chosen box and show a small card: action, top probabilities, p(done),
  p(risky), latency. Remove the overlay before acting. The model never sees the overlay.
- Sweep runner: a list of (scenario, task, seed, model) jobs spread over several blink servers,
  N concurrent browsers, resumable, writing `runs/<run_id>/results.jsonl` and an aggregate table.
- Run locally or with the example Dockerfile. Supply a self-hosted server URL, and keep the
  offline apps served on loopback. See `README.md` for setup and a CPU-only mock.
